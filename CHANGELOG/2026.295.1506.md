# 2026.295.1506 — fix(kindcluster): map containerd to nerdctl, refuse unknown engines

## Summary

Fixes the silent wrong answer in `deploy:kindcluster`: the engine word was resolved
with `container.EngineBinary`, whose contract maps an **unknown** word to
`spec.DefaultContainerEngine` (`podman`), and the result was used directly as kind's
`KIND_EXPERIMENTAL_PROVIDER`.

With `spec#266` the engine vocabulary is `podman | docker | containerd`; `containerd`
is driven through its `nerdctl` CLI. On this repo's previous pin, and on the
`v2026.276.1350` tag the `check-kindcluster-*` bed pins (`spec v0.2026273.203`,
vocabulary `podman/docker/nerdctl`), `engine: containerd` therefore provisioned a
podman-backed kind cluster and reported success.

- **Bump** `spec` to `v0.2026295.1243` and `sdk` to `v0.2026295.1359` (the
  `WorkloadUser` mode split the new `EngineCapability` requires; the old sdk does not
  compile against the new spec).
- **Map** the engine word to kind's provider from the spec capability data, not a
  literal: `container.EngineCapabilityFor(word).Binary` gives `containerd → nerdctl`,
  `docker → docker`, `podman → podman`. One named function,
  `kindProviderForEngine` (`candy/plugin-kube/kindcluster.go`).
- **Refuse** any word outside `spec.EngineNames`, naming the supported set — no
  fallback (R3). The error is built from the spec's closed vocabulary so it cannot
  drift.
- **Keep the engine WORD** for local-image resolution (`resolveWorkloadImage`), and
  invoke the kind provider word directly in `kindSaveImageArchive` /
  `kindNodeHasImage`. Feeding `nerdctl` back through `EngineBinary` would re-read it
  as an unknown engine word and fall back to podman — the same defect one level down.
- **Sweep** three stale "direct local podman storage access" comments in
  `preresolve.go` / `materialize.go` to "local engine storage" (R1/R5 claim sweep).
