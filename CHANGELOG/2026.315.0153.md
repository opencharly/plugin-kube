# 2026.315.0153 — fix(kube)!: remove the verb's two mutation methods — a verb observes (D-VERB-1)

## Summary

`DESIGN.md` §23 states **D-VERB-1**: *"A verb observes and never changes state: a state change is a
field (§14.4), and the one step that changes state is a `run:` step (D-VERB-5)."* The `kube:` verb
shipped thirteen methods, and **two of them write to the cluster**. Measured at `origin/main`
`df96229`:

| site | what it does |
|---|---|
| `methods.go:44` | `"apply": {"manifest"}` in `requiredModifiers` |
| `methods.go:45` | `"delete": {"manifest"}` in `requiredModifiers` |
| `methods.go:89-92` | `case "apply": return runApply(…)`, `case "delete": return runDelete(…)` |
| `methods.go:512,521` | `runApply` calls `iface.Create`, then `iface.Update` on `AlreadyExists` |
| `methods.go:556` | `runDelete` calls `iface.Delete` |
| `schema/kube.cue` | `method: (… \| "apply" \| "delete" \| …)`, plus `manifest?: string`, which only they read |

Every other method observes: `nodes`, `wait-nodes`, `pods`, `wait-ready`, `ingress`, `ingressclass`,
`storageclass`, `service`, `lb-external-ip`, `addons`, and `raw` (whose only API calls are
`iface.Get` and `iface.List`, `methods.go:588,594`).

**What the premise measured to.** `TODO.md` 12.7 says the verb "exposes `apply` and `delete`, which
are mutations". The tree agrees exactly — and the *blast radius* is what the row does not say. **No
authored config in the org reaches either method, in any of the three spellings the verb admits.** A
sweep of every submodule's `origin/HEAD` tip — **430 repos**, the map key `method:`, the scalar
`kube: <word>` sugar, and a nested key — returns **0** hits for the two words, while the same
predicates return **4** (`method: nodes`) and **3** (`kube: nodes`) for a live observation method.
The predicate is calibrated, not merely empty. So the fix is a deletion with an **empty migration**,
not a rename that rewrites authored config.

**Why deleting is the right remedy rather than reclassifying.** The design already says what each of
the two did belongs to: the workload lowering (`deploy.go`'s `kubectl apply -k` on the
egress-validated Kustomize tree), the `package: helm:` action, or a `command:` step (`TODO.md` 12.7).
The `helm:` side of the same row is already observation-only — `plugin-helm`'s verb serves exactly
four methods, `release-exists`, `status`, `revision`, `values-hash` (`git -C plugin-helm grep -n
'case "' origin/main -- candy/plugin-helm/helm.go` → 4 hits, `helm.go:150,152,154,156`) — so this
change closes the one remaining mutation arm of that class.

**What this change does.** Removes both methods and every part that existed only to serve them: the
two `requiredModifiers` entries and the two dispatch cases; `runApply` and `runDelete`;
`readYamlDocs`, `gvrForObject` (`methods.go`) and `kindToPluralResource` (`cluster.go`), the last
users of the manifest path; the four now-unused imports (`errors`, `io`, `os`, `yamlutil`); and
`#KubeInput.manifest`, with `params/` regenerated by the sanctioned pipeline. The served schema is
what closes it for authored input: `#KubeInput` refuses `method: apply`, `method: delete` and
`manifest`, while admitting all eleven observation methods — at the boundary the host validates
every authored step at (`def.Unify(input).Validate(cue.Concrete(true))` in charly's
`validateAuthoredPluginInput`).

This is `TODO.md` item **12.7**, tracking issue **opencharly/plugin-kube#32**, under the campaign
sequence **opencharly/opencharly#950**. It adds no row to the D-PAT census and moves none
(**opencharly/opencharly#945**).

## Change classification

Plugin surface change inside `github.com/opencharly/plugin-kube/candy/plugin-kube` — the `verb:kube`
capability's method enum and dispatcher. No image is built here and no deploy target moves.

- **What changes for a consumer:** an authored `kube:` step carrying `method: apply` or
  `method: delete`, or a `manifest:` field, is now refused — at load by the served `#KubeInput`
  schema, and at dispatch as `unknown kube method`. An authored `kube:` step using any of the eleven
  observation methods loads and runs exactly as before: byte-identical verdicts for `nodes`/`pods`
  against the same live cluster (§3).
- **Who is affected:** nobody in the org's tree — 0 authored uses across 430 repo tips in all three
  spellings (§4), so the pin bump needs no config migration anywhere.

**Breaking change + rollback:** it breaks exactly one class — an authored `kube: {method: apply}` or
`{method: delete}` step (or a `manifest:` field beside an observation method). That class is empty
in the org: 0 of 430 repo tips author either word, and the umbrella root's own `charly.yml` authors
no `kube:` step at all. The migration for anyone outside the org who DID author one is the one the
design already names: the state change becomes a deploy (`kubectl apply -k` on the egress-validated
tree, which is `charly deploy add`), a `package: helm:` action, or a `run:` step. Rollback is the
previous release tag: the plugin carries no on-disk state, the field is gone from the served def,
and there is no migration to undo — re-pinning to the tag before this merge restores the two
methods verbatim.
